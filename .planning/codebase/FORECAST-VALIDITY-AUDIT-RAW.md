Nothing asserts the forecast row's existing business_id matches. For a coach/admin session (RLS-permitted across clients), any client-side state bug that pairs business A's id with business B's forecastId would silently RE-HOME business B's forecast into business A — assumptions, goals and fiscal window overwritten — and the subsequent activation would deactivate business B's real active forecast for that FY. Given dual-ID/state-staleness is this codebase's #1 recurring incident class, the missing ownership assertion is the one cheap invariant that would turn that class of bug into a 403 instead of silent cross-client data corruption.
IMPACT: No live incident traced, but the failure mode is a coach switching clients mid-session with a stale wizard state: one autosave rewrites another client's forecast row to the wrong business. A one-line `.eq('business_id', profileId)` on the update (and a row-ownership check before the RPC create path) closes it.

## [P2] PROC-10 — The recompute recovery hatch re-materializes from assumptions that draft autosaves have since overwritten
CLAIM: Draft autosaves on the update path deliberately keep writing `assumptions` (draft-publish-guard strips wizard_state/goals but not assumptions — 'a draft update saves WORK'). The recompute route re-derives forecast_pl_lines from the CURRENT assumptions column ('Re-derives forecast_pl_lines from the CURRENT financial_forecasts.assumptions row', header comment). So after any mid-edit autosave, running the documented recovery hatch on the active forecast publishes half-edited draft assumptions into the live P&L lines while wizard_state still carries the previously approved summary — the exact drafts-never-materialize invariant of #350, violated through the side door the remediation runbook points at.
IMPACT: The D-18 staleness invariant will legitimately flag forecasts whose updated_at moved past computed_at (which every draft autosave causes) — and the prescribed fix, recompute, then installs the draft's numbers as the published budget. Guard: recompute should refuse (or warn) when the row's updated_at postdates completed_at, or drafts should write assumptions to a separate column.

## [P2] PROC-11 — In-progress draft rows become unreachable when the wizard reopens without an explicit forecast id
CLAIM: The draft identity guard discards a localStorage draft whenever its owner id differs from the requested id — including requested=null. A session that started fresh gets a server draft row (is_active=false) via autosave and stamps its id on the local draft; if the wizard later reopens through an entry point that passes existingForecastId=null (forecast/page.tsx passes selectedForecastId which resets to null on completion and on several paths), the local draft is discarded (`owner !== requested` with requested null), and the mount path auto-discovers `versions.find(is_active) || versions[0]` — the ACTIVE forecast, not the draft. The operator's in-progress draft still exists server-side but nothing resurfaces it; the wizard silently opens a different forecast.
IMPACT: A client builds half a forecast, closes the tab, and comes back via the generic Forecast page: the wizard opens showing last quarter's active forecast instead of their half-built draft, which looks like total work loss unless they find the draft row in the version selector. Compounded by the single localStorage slot per (business, FY) shared across all scenarios.

## [P2] XVAL-5 — Stored forecast lines carry synthetic account codes ('revenue-0', 'ACCT-MISSING-<uuid>', client-random ids) — per-line budget↔actual joins on account_code cannot match
CLAIM: convertRevenue/convertCOGS/convertOpEx store the wizard's in-memory line id as account_code when no existing code is found (`account_code: existing?.account_code || revLine.accountId`, lines 209/286/427). In production this yields codes like 'revenue-0'…'revenue-17' (JDS, Dragon, IICT, Digital Bond — these ids come from Step 2's `revenue-${idx}` seeding), timestamp-random ids like '1781828347010-cvgvmt63m' (Digital Bond, from a client-side id generator), and 'ACCT-MISSING-<uuid>' (Envisage FY26, from the D-44.1-05 backfill). ForecastReadService's own doc (forecast-read-service.ts:512-515) warns that consumers keying on account_code lose fidelity; any budget-vs-actual join on account_code against real Xero codes silently matches nothing for these lines, and the codes are also index-position-dependent ('revenue-3' means a different account per business and per reseed).
IMPACT: Any current or future consumer that matches stored budget lines to Xero actuals by account_code (monthly-report auto-map, per-line variance features) gets no match for most of JDS/Dragon/IICT/Digital Bond's revenue lines and falls back to name matching or shows blank budgets; a Step-2 reseed that reorders accounts silently re-labels which real account 'revenue-3' refers to. ## [P2] XVAL-8 — xero_accounts hygiene: Envisage's full CoA duplicated under tenant_id NULL; stale IICT tenant copies under 'Wisdom BI'; duplicate/blank account codes in 8 of 14 tenants
